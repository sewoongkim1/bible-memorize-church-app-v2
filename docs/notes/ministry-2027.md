      (예: 찬양부 비파와수금·베데스다 유무, 목양부 정착관리 vs 목양관리)
      **개발보다 데이터 확정이 먼저**다. 그 확인용 엑셀 양식(`tools/ministry-form-gen.py`
      → `ministry/2027_사역신청_부서확인양식.xlsx`, 94팀·2026-09-07 찬양부 확정 반영)은
      이미 있다 — 부서 확인이 끝나면 그 표기명이 `ministry_catalog` 최종 시드가 된다.
      필사 노트 신청과 같은 뼈대(신청/취소/상태전환+Web Push)를 재사용할 계획.
      ⚠️ **두 원본 다 사역 시간·요일·하는 일이 없다**(2026-09-07 지적) — 이름만 봐서는
      성도가 「오병이어 1팀·2팀」 차이를 모른다. 같은 양식에 칸을 더해
      **이름 확인과 한 번에** 걷도록 고쳤다(두 번 물으면 부서 응답이 늦어진다).
      **필터용 칸을 더해 양식이 14칸 → 24칸이 됐다.** 성도 화면 필터가 읽는 것이 이
      칸들이다 — **문장으로 쓴 「매주 화 오전 10시」는 기계가 못 읽어서**, 사람이 읽을
      문장과 기계가 읽을 칸을 따로 받는다. 표는 네 묶음(①이름 ②언제 ③안내 ④확인)이고,
      왼쪽 A~G는 보기만·오른쪽 H~X가 전부 부서 기입이다.
      **2026-09-10 「② 언제」 확정(성도님 지시)** — `supabase/ministry_when_v2.sql`:
        · 요일 넷: **주일 · 금요일 · 토요일 · 평일** (`day_sun`·`day_fri`·`day_sat`·`day_week`)
        · 주기 넷, **여러 개 고를 수 있다**: 매주 · 격주(교대형식) · 매달 · 그때그때
          (`freq_weekly`·`freq_biweekly`·`freq_monthly`·`freq_adhoc`)
        · 시각 둘: **주일에만** (`time_from`·`time_to`)
      ⚠️ **금요일은 「평일」이 아니다.** 금요성령집회·행복전도대(금)처럼 금요일 사역이
      많아 따로 뺐다 — 그래서 「평일」은 **월~목**이다. 화면·양식 라벨에도 그렇게 적었다.
      ⚠️ **주기는 「팀이 모이는 주기」가 아니라 「한 사람이 서는 주기」다** — 당번을
      넷이 돌면 팀은 매주라도 한 분은 매달이고, 성도님이 재는 것은 자기 부담이다.
      ⚠️ **시각은 주일 사역에만 받는다**(성도님이 그 결과를 알고 고르셨다: 평일·금요일·
      토요일 팀은 「몇 시쯤」 필터에 안 걸린다 — 새벽기도·금요집회 포함. 그 팀들의 시간은
      「사역 시간·요일(문장으로)」 칸에 글로 적는다). 규칙을 **DB 에도** 새겼다
      (`ministry_catalog_time_sun_chk`) — 코드에만 두면 다음 사람이 서버를 고칠 때 깨진다.
      서버는 주일을 끄면 시각을 **미리 비운다**(안 그러면 제약에 걸려 저장이 통째로
      실패하고 관리자에게는 까닭 없는 오류로 보인다). 「보내온 칸만 고친다」 규칙 때문에
      `day_sun` 이 요청에 없을 수 있어 그때는 **DB 값을 읽는다.**
      ⚠️ **옛 `freq` text 한 칸과 그 CHECK 제약은 지웠다.** 「같은 뜻이 두 곳」이면
      나중에 한쪽만 고치게 된다(같은 날 직분 목록에서 겪었다 — 아래 참고).
      ⚠️ **비어 있음은 「모름」이지 「해당 없음」이 아니다** — 미기입을 제외로 짜면
      회신율이 곧 실종률이 된다. 안 적은 팀은 「정해진 날 없음·때마다 다름」으로 남는다.
      ⚠️ **사슬이 일곱이다: DB · 서버 · 어드민 · 성도 필터 · 양식 → 취합 → 시드 SQL.**
      한 곳만 고치면 화면은 멀쩡한데 저장이 조용히 안 걸리거나, 부서가 채워도 DB 까지
      닿지 않는다(`ministry-form-gen.py` · `ministry-merge-replies.py` ·
      `ministry-seed-sql.py`). 취합은 **칸 번호가 아니라 칸 이름으로** 찾는다 —
      번호를 박아 두면 칸이 늘 때 조용히 엉뚱한 값을 읽는다(오류도 안 난다).
      시드는 **부서가 하나도 안 적으면 DB 의 기존 값을 덮지 않는다**(개발에서 47건 보존 확인).
      ⚠️ **직분 목록은 세 곳에 있다**(`app.js` MIN_POSITIONS · `index.ts` allowlist ·
      DB CHECK). 2026-09-10에 앞의 둘에만 「사모」를 더해 **화면엔 뜨는데 신청이 500 으로
      막혔다** — 그 500 은 성도님께 「연결이 고르지 않아…」로 보여 까닭조차 안 보인다
      (`supabase/ministry_position_samo.sql`). 허용 목록에 값을 더할 땐 그 칸에 CHECK 가
      있는지 먼저 볼 것: `select conrelid::regclass, conname, pg_get_constraintdef(oid)
      from pg_constraint where pg_get_constraintdef(oid) ilike '%전도사%';`
      **어드민(🗂️ 사역팀 정보)에서 고칠 수 있는 것**: 설명 네 칸(시간·요일 문장 / 하는 일 /
      필요 인원 / 지금 섬기는 분) + 「② 언제」 + **같은 위원회 안의 차례(▲▼)**.
      ⚠️ **팀 추가·삭제·이름 바꾸기는 어드민에서 하지 않는다**(성도님 결정 2026-09-10 —
      "나머지는 엑셀에서"). 그쪽 원본은 부서 확인 엑셀 → JSON → 시드다. 어드민에서 만들면
      엑셀과 DB 가 갈라지고 **다음 시드에 조용히 지워진다.** 차례도 시드를 다시 돌리면
      엑셀 차례로 돌아간다(그게 맞다 — 구조의 원본은 엑셀이다).
      **2026-09-07 — 앱이 열리기 전까지는 올해도 종이로 받는다**(성도님 확정:
      "현재와 같이 교인들에게 나누어 주고, 제출하는 방식으로 A4 2장"). 그 초안을
      `tools/ministry-apply-form-gen.py` → `ministry/2027_사역신청서_A4.pdf`로
      만들었다 — `ministry_catalog_2027_draft.json`을 그대로 읽으므로 팀명이
      바뀌면 다시 돌리기만 하면 된다. 임명직은 별도 상자가 아니라 **같은 자리에
      회색 비활성 칸**으로 둔다(2026-09-07 — 부서 전체 구조가 한 목록에서 보이는
      편이 낫다). ⚠️ **아직 초안 이름 그대로**라 부서 확인 전엔 인쇄해 나눠주지 말 것.
      **2026-09-07 — 찬양부·전도부 첫 확인 결과 반영**: 성도님이 찬양부 세부

      찬양팀운영·주나힘찬양 제외)와 전도부 행복전도대(그룹→독립 항목 2개)를
      확정해 `ministry_catalog_2027_draft.json`·확인 양식·종이 신청서 세 곳에

## 사역신청 담당자 화면 (2026-09-17)

사역 담당자는 관리자 메뉴 전체를 볼 필요가 없다 → **`admin-ministry.html`**(담당자에게 드리는 주소)이
`admin-stats.html?only=ministry` 로 넘겨 **「사역신청 현황」·「사역팀 정보」 두 메뉴만** 보인다.
화면을 따로 만들지 않은 까닭: 두 메뉴를 두 곳에서 따로 고치면 반드시 어긋난다. 담당자는 **모든 사역신청
자료를 본다**(부서별로 나누지 않는다 — 성도님 결정, 나머지는 기존 절차).

- **들어오는 조건은 둘 다:** ① 사역신청 암호(시크릿 `MINISTRY_SECRET`) ② **등록된 담당자**
  (app_config `ministryAdmins`, identity_key 배열 — 교구·목장·이름을 앱 로그인과 같게 받는다).
  **관리자 암호(`ADMIN_SECRET`)는 담당자 확인 없이** 통과한다(관리자는 모든 것을 본다).
- ⚠️ **같은 관리자 암호를 드리면 안 된다.** 메뉴를 숨겨도 그 암호 하나로 관리자 액션 50여 개(알림 발송·
  성도 정보 변경·찬양/말씀 앱 관리)를 다 부를 수 있다. 사역 암호는 **`ministryList`·`ministrySetStatus`·
  `ministryCatalogSave`·`ministryCatalogOrder` 넷만** 받는다(`ministryAdminError`). `authCheck`(허브)·`stats`
  ·`sendPush` 는 사역 암호로 막히는 것을 개발에서 확인했다(12가지 경우).
- ⚠️ **담당자 확인은 액션마다** 한다 — 로그인 화면에서 한 번만 보면 API 를 바로 부르는 사람은 건너뛴다.
  그래서 화면은 네 액션에 `staff`(교구·목장·이름)를 늘 함께 보낸다. 목록에 있어도 **users 에 없는 키는
  통과시키지 않는다**(오타로 넣은 키가 문을 열지 않게). 목장은 「20목장」으로 적어도 「20」과 같게 본다.
- 이름·소속은 비밀이 아니다 — **암호와 함께일 때만** 뜻이 있다(로그인은 모르는 이름이면 계정을 만들어 준다).
- 저장 칸을 나눈다: 담당자 화면은 sessionStorage `ministry-pw`·`ministry-staff`. `admin-pw` 에 담당자
  암호가 들어가면 허브·다른 도구가 그 암호로 부르다 줄줄이 실패한다.
- **담당자 등록은 관리자 화면 「🔑 사역신청 담당자」**(관리자 암호로만 — 사역 암호로 담당자를 더할 수 있으면
  그 암호 하나로 스스로 문을 연다). 이름으로 찾아(`adminFindMembers`) 소속·마지막 접속을 보고 골라 **한 분씩**
  추가·빼기(`ministryAdmins`·`ministryAdminsSave`). 저장 뒤 **다시 읽은** 목록을 돌려주고, 화면은 저장 중에
  단추를 모두 잠근다(읽고-고쳐-쓰기라 겹치면 한쪽이 덮인다). `supabase/ministry_admins.sql` 은 목록을 통째로
  바꾸므로 **화면으로 넣은 분이 지워진다** — 이제 쓰지 않는다. 코드에 이름을 두지 않는다(공개 저장소).
  **등록하지 않으면 사역 암호로는 아무도 못 들어온다.** 운영 첫 등록: 2026-09-17.
- **담당자 확인은 키가 아니라 사람(user_id)으로** 한다 — 관리자가 이름·소속을 고치거나 계정을 합치면
  users.identity_key 가 바뀌고 옛 키는 `user_identity_aliases` 로 간다. 키끼리 비교하면 새 소속으로도 옛 소속으로도
  막혔다(리뷰에서 발견). 앱 로그인이 별칭을 따라가듯 등록 키·적은 키를 둘 다 사람으로 풀어 맞댄다. 명단 화면은
  그런 분을 지금 소속으로 보이고 「등록한 뒤 이름·소속이 바뀐 분」이라고 적는다(`moved`).
- ⚠️ **틀린 암호와 「맞는 암호 + 담당자 아님」은 같은 답(`unauthorized`)** — 답을 가르면 담당자를 몰라도
  사역 암호가 맞았는지 알아낼 수 있다(리뷰). 로그인 화면도 한 문장으로 안내한다.
- 적은 표기 차이는 받아 준다: 목장 「20」·「20목장」(목장 이름이 「…목장」인 분 때문에 적은 그대로도 본다),
  학년 「3」·「3학년」(앱은 「예: 3학년」). DB 오류는 삼키지 않는다(「담당자 아님」으로 보이면 까닭 없이 막힌 줄 안다).
- 열린 담당자 화면이 권한을 잃으면(빠짐·암호 교체) 로그인으로 돌려보낸다(`minAuthLost`), 메뉴를 열 때도 한 번 되짚는다.
- 2026-09-17 **3관점 리뷰 워크플로**(보안·정확성·화면, 반박 검증)에서 확인된 6건(모두 낮음)을 위와 같이 고쳤다.
- 개발 DB 에는 시험용 「교구 사랑 1목장 사역담당시험」 한 분만 등록돼 있다.
- ⚠️ `hidden` 속성은 `display:flex` 를 못 이긴다 — 로그인 칸 교구/교회학교 줄에 `[hidden]{display:none}` 을 뒀다
  (없으면 두 줄이 다 보였다).

### 사역신청 현황 — 보기·필터 (2026-09-17)
- **보기 셋: 건별 · 사람별 · 사역별.** 묶음 안의 카드는 건별과 **같은 카드(`mnCard`)** — 어느 보기에서나 상태를
  바꿀 수 있다. 묶음은 접혀 시작하고, 펼친 묶음은 상태를 바꿔 다시 그려도 그대로(`mnOpen`). 사역별은 신청 많은 순,
  사역별 보기에서는 같은 숫자인 「팀별 신청 수」 칸을 숨긴다.
- **신청일 필터**(시작~끝, 비우면 전체) — 받아 둔 명단에서 바로 추린다. `r.at` 은 KST 날짜(YYYY-MM-DD)라 문자열 비교로 된다.
- 조회·찾기 단추(`.push-btn`)에 규칙이 없어 브라우저 기본 회색 작은 단추였다 — 남색 · 높이 46px 로 공용 규칙을 뒀다

### 중복 신청 · 미채택 삭제 · 취소 사유 (2026-09-17)
- **왜:** 한 분이 교구를 잘못 넣고 로그인(새 계정이 만들어진다) → 신청 → 원래 소속으로 다시 로그인 → 같은 사역을
  또 신청해 **같은 분·같은 사역이 두 건**씩 생겼다(운영, 휴대폰 번호 같음). 사역신청은 계정마다만 중복을 막는다.
- **신청할 때(서버 `ministryApply`):** 새 사역을 더할 때 **같은 이름 + 같은 휴대폰 번호**로 다른 계정의 신청이 있으면
  저장하지 않고 `{ok:false, confirm:"dup-phone", message}` 로 한 번 묻는다 → 앱 `minConfirm` 「그래도 신청」이면
  `dupOk:true` 로 다시 보낸다. 막지 않고 묻는다. 상대 소속은 알려 주지 않는다.
  ⚠️ **문구를 `error` 에 넣으면 안 된다** — `supaCall` 은 `error` 가 있으면 던져서 되묻기 창을 못 띄우고 막다른 알림이
  된다(리뷰 워크플로에서 잡았다 · 서버 응답을 가짜로 갈아 끼워 시험하면 이 문제가 안 보인다 — **실제 서버로** 시험할 것).
  ⚠️ **이름까지 같을 때만** 묻는다 — 번호만 보면 아무나 번호를 넣어 「그 번호로 신청이 있나」를 알아낼 수 있고,
  번호를 함께 쓰는 가족에게도 괜히 묻는다.
- **담당자 화면:** 같은 번호로 여러 사람(이름/소속)이 신청했으면 카드와 사람별 머리에 표시 —
  이름이 같으면 「⚠️ 같은 이름·번호 · 다른 소속(…)에서도 신청」, 이름이 다르면 「☎️ 같은 번호 · 다른 신청자(…)」.
  명단 **전체**로 센다(필터로 한쪽이 가려져도 표시는 남는다). 번호는 결정이 나면 지워지므로 남은 것끼리만 본다.
- **「미채택」 상태를 뺐다**(성도님 결정) — 화면 `MN_STATES`·서버 `MINISTRY_STATUS`. 운영에 미채택 행은 없었다.
  서버·앱의 미채택 분기와 DB CHECK 는 옛 행이 있어도 깨지지 않게 남겼다(좁히려면 개발→운영 마이그레이션).
  임명되지 않은 분은 「취소」+사유로 정리한다.
- **취소 사유:** 브라우저 `prompt` 대신 화면 안 창(`mnAskCancelReason`) — 사유가 비면 「취소하기」가 안 눌리고,
  자주 쓰는 사유를 눌러 채운다. 목록을 불러올 때 사유(`note`)도 담는다(전에는 새로고침하면 사라졌다).
  바깥을 **눌렀다 뗄 때 모두** 바깥이어야 닫힌다(사유를 끌어 선택하다 밖에서 떼면 글이 사라졌다).
- 상태 칩 맨 앞에 **「전체」**, 칩 줄은 줄바꿈(옆으로 밀려 잘리던 것). 카드의 전화·알림 줄은 상태 단추 기둥 아래로
  빼 카드 전체 폭을 쓴다(두 줄로 꺾이던 것).
