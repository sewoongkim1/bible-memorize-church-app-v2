성도님 안내(주보·게시판·설명)와 담당자 교육에 그만큼 걸린다.

| 주 | 단계 | 끝나야 하는 것 |

## 1. 백엔드 — 테이블 2개 + 액션 6개

### 1-1. 스키마 (`supabase/ministry.sql`)

```
ministry_catalog
  id, year, committee, group_name, team, kind('apply'|'appoint'),
  schedule_note, desc_note, capacity_note, option_note, sort_order
  unique(year, committee, group_name, team)

ministry_orders
  id, year, identity_key, name, gu, mokjang,
  choices jsonb,              -- [{catalog_id, option}] 최대 3개, 순위 없음
  status('신청완료'|'검토중'|'임명확정'|'미채택'),
  note, created_at, updated_at, decided_at, notified_at
  unique(year, identity_key)  -- 한 해에 한 사람 한 건
```

⚠️ **RLS를 그 자리에서 켠다**(`enable row level security`). `event_entries`가
이걸 빠뜨려 `user_id` 47건이 공개 키로 읽혔다 — 같은 실수를 반복하지 않는다.
`anon`·`authenticated`에게 SELECT 권한을 주지 않고, Edge Function(service_role)만
읽고 쓴다.

⚠️ **`notified_at`은 필사 신청과 같은 역할** — 푸시를 두 번 보내지 않기 위한 자리다.

⚠️ **개발 DB에 먼저 올린다**(`ktpwthwqzgcqcrmsafdo`). 운영은 5단계에서.

### 1-2. 액션 6개 (`supabase/functions/api/index.ts`)

필사 신청(`pilsa*`)을 그대로 본뜬다 — 새로 발명하지 않는다.

| 액션 | 주체 | 하는 일 | 본뜰 것 |
|---|---|---|---|
| `ministryCatalog` | 공통 | 연도별 팀 트리 반환(임명직 포함, 화면에서 잠금) | — |
| `ministryApply` | 성도 | 최대 3개 저장. 기간 밖이면 거절 | `pilsaApply` |
| `ministryMine` | 성도 | 내 신청 1건 조회 | `pilsaMine` |
| `ministryCancel` | 성도 | 마감 전 취소 | `pilsaCancel` |
| `ministryList` | 관리자 | 부서·상태별 목록 | `pilsaList` |
| `ministrySetStatus` | 관리자 | 상태 전환 + 임명확정 시 푸시 1회 | `pilsaSetStatus` |

⚠️ **응답에 `user_id`를 절대 싣지 않는다.** 이 API는 JWT가 없어 남의 `user_id`
하나면 그 사람 행세가 된다(게시판 `boardList`가 실제로 그랬다). 필요한 것은
「내 것인가」뿐이므로 `isMine` 참/거짓만 내려준다.

⚠️ **서버가 3개 제한을 다시 검사한다.** 화면에서 막는 것은 편의고, 규칙은 서버가
지킨다(`choices` 길이 > 3이면 거절).

⚠️ **기간 검사도 서버에서** 한다. 기간은 `app_config`에 둔다 —
`{"ministry": {"year": 2027, "open": "2026-12-13", "close": "2026-12-27"}}`.
날짜를 코드에 박으면 바뀔 때마다 배포해야 한다.

**완료 기준**: 개발 DB에서 curl로 6개 액션이 모두 기대대로 답한다.
⚠️ 한글은 명령줄 리터럴로 보내지 말고 **UTF-8 파일을 body로** 보낸다(깨져서
서버 버그로 오인한 적이 있다).

## 2. 성도 화면

`index.html` + `app.js`. **데모(`ministry/2027_사역신청_데모.html`)가 이미
흐름과 부품을 확정해 두었다** — 그대로 옮기면 된다.

| 화면 | 내용 | 재사용 |
|---|---|---|
| 안내 | 임명 원칙 6조 + 기간 안내 | 필사 신청 안내 화면 |
| 부서 고르기 | 위원회 아코디언, 최대 3개, 임명직 잠금 | 가정 축복 기도문 `.pr-acc` |
| 확인 | 고른 것 + 빼기 → 제출 | — |
| 내 신청 | 상태 + 목록, 마감 전 수정·취소 | 필사 신청 내역 카드 |

⚠️ **순위를 넣지 않는다**(08-1장). 화면에 번호를 붙이지 않는다.

⚠️ **첫 화면 진입점은 기간에만 뜬다.** 「함께」 묶음에 한 줄. 기간 밖에는 아예
안 보인다 — 상시 기능이 아니다. 새 단추에 제 색을 주지 않는다(연한 남색,
「색은 위계다」).

⚠️ **`renderMinistry` 같은 새 이름을 짓기 전에 `grep`** 한다 — `renderBlessing`이
이미 로그인 축복 인사에 쓰이고 있어 하마터면 겹칠 뻔했다.

⚠️ 배포는 **`python tools/bump.py` 한 번** — 캐시태그·판 번호·`APP_BUILD`가 함께 오른다.

**완료 기준**: localhost(개발 DB)에서 신청 → 수정 → 취소가 되고, 3개 초과가 막힌다.

## 3. 관리자 화면

`admin-stats.html`에 **탭 하나**로 붙인다. 새 페이지를 만들지 않는다.

- 부서·상태별 목록, 신청자(교구·목장·이름), 고른 사역 3개
- 상태 전환 4단계, **임명확정 시 푸시 1회**
- 푸시 결과를 **보냄 / 안 켜심 / ⚠️ 발송 실패** 셋으로 구분해 보여준다 —
  실패를 「안 켜심」으로 뭉뚱그리면 푸시가 고장 나도 아무도 모른다(필사 신청에서
  겪은 것).
- 부서별 집계(몇 명이 신청했는지) — 담당자가 가장 먼저 궁금해하는 숫자다.

⚠️ **알림을 안 켠 분에게는 게시로 알린다.** 화면이 「이 사람은 푸시를 못 받는다」를
알려 줘야 담당자가 게시·연락으로 메운다.

## 4. 기간 노출 · 안내

- 첫 화면 배너: `app_config`의 기간을 읽어 **자동으로 뜨고 사라진다**
- 게시판 공지(작성자 「방송전산부 전산팀」) 1건
- 종이 신청서와 **문구를 맞춘다** — 같은 원칙 6조, 같은 「최대 3개」
- 마감 3일 전 리마인드 푸시 1회 (선택)

---

## 5. 운영 반영 + 리허설

1. `supabase/ministry.sql`을 **운영 DB**에 적용
2. 확정본 JSON을 운영 `ministry_catalog`에 시드
3. Edge Function 운영 배포 — **개발 먼저 확인한 뒤**
4. `python tools/bump.py` → 푸시 → 배포 확인(**`APP_BUILD` vs `?v=` 대조**)
5. **담당자와 한 번 돌려 본다** — 신청 한 건을 넣고 임명확정까지 눌러 본다.
   푸시가 실제로 오는지 실기기에서 확인.

⚠️ **리허설로 넣은 시험 신청은 지운다.** 통계에 섞이면 첫날 숫자가 틀어진다.

## 하지 않기로 한 것 (1차년도)

넣고 싶어질 때 이 목록을 먼저 본다.

- **겸직 자동 검증** — 누가 어느 부서 팀장인지 시스템이 모른다. 담당자가 눈으로 본다
- **정원 관리** — `capacity_note`는 참고 문구일 뿐, 꽉 찼다고 막지 않는다
- **우선순위** — 08-1장에서 뺐다
- **교적시스템 연동** — 별개로 만든다. 교적에는 따로 입력한다(기획(안) 확인 사항)
- **쓰기·채점·진행률** — 이건 「외우는 것」이 아니라 「신청하는 것」이다
