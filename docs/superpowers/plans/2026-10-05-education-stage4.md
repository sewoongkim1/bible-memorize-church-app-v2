# 교육신청 4단계 — 앱 알림 · 교인명부 교육 이력 탭 · 교육 통계 (2026-10-05)

> 설계 `docs/superpowers/specs/2026-10-05-education-courses-design.md` §11 4단계. 1~3단계(신청·담당자·출석부·수료증·진위 확인)는 운영 중(게이트 닫힘).

## 친구 결정 (2026-10-05)

| 무엇 | 정함 |
|---|---|
| 4단계 범위 | **앱 알림 · 교인명부 「🎓 교육」 탭 · 📊 교육 통계** — 사역신청 선수 조건은 **하지 않는다** |
| 알림 때 | **확정됐을 때**(담당자가 확정 · 대기에서 확정으로 올라감) · **개강 전날**(첫 회차 전날 저녁) |

- 성도님이 선착순 강좌에 신청하자마자 확정된 경우는 화면이 바로 「확정됐어요」라고 하므로 알림을 보내지 않는다.
- 개강 전날 알림은 **저녁 7시(KST)** 한 번 — 첫 회차 날짜(없으면 교육 시작일)가 내일인 강좌의 확정자에게.

## A. 앱 알림

- **보내는 길 하나**: 성경암송 `api` 에 내부 전용 액션 **`internalEduNotify({kind:'confirmed', enrollment_ids})`** — 사역 임명 알림(`internalMinistryNotify`)과 같은 문(같은 프로젝트 서비스 키를 `x-internal-key` 로 받은 때만) · 발송은 기존 `pushToSubs`(웹 푸시·아이폰 APNs·플레이 앱 · `push_log` 기록)를 그대로 쓴다.
- **한 번만**: v2 `edu.sql` 에 `edu_notify_log(enrollment_id → edu_enrollments on delete cascade, kind check in ('confirmed','first_day'), sent_at, primary key(enrollment_id, kind))` · RLS · service_role 만 — 같은 신청에 같은 알림은 한 번(취소 뒤 다시 확정돼도 다시 안 보냄 · 받는 기기가 없어도 「보냄」으로 적어 재시도 폭주를 막는다).
- **부르는 곳**:
  - 교회 어드민 `eduEnrollSet`(확정 · 다른 op 의 `promoted`) · `eduEnrollAdd`(앱 계정이 있는 분이 확정으로 들어갈 때) · `eduCourseSave`(정원 늘려 `edu_course_refill` 이 올린 분들) → 저장이 끝난 뒤 `internalEduNotify` 를 부른다(실패해도 저장은 성공 · 결과에 `notified`/`notifyError` 만).
  - 성경암송 `eduCancel`(성도님 취소로 대기 분이 올라감) → 같은 함수를 안에서 바로.
- **개강 전날**: `api` 내부 액션 **`internalEduRemind()`** — 내일(KST) 첫 날인 강좌(초안·보관·마침 빼고)의 확정자 중 앱 계정이 있고 `first_day` 로그가 없는 분께 · pg_cron(매일 **10:00 UTC = 19:00 KST**)이 기존 푸시 크론과 같은 방식(pg_net · 서비스 키)으로 부른다 — `supabase/edu_remind_cron.sql`(개발 먼저 · 다시 돌려도 안전 · 기존 크론 이름과 겹치지 않게).
- **문구**(알림 제목 「🎓 교육」):
  - 확정: 「{과정} 신청이 확정됐어요 — 첫 시간 10월 25일(일) 14:00」(첫 회차 없으면 앞부분만)
  - 대기에서 확정: 「자리가 나서 {과정} 신청이 확정됐어요 — 첫 시간 …」
  - 개강 전날: 「내일 {과정} 첫 시간이에요 — 14:00 · 본당」
- **누르면**: 앱이 그 강좌 자세히로 연다(`/?edu=<강좌 id>` 같은 딥링크 — 앱이 이미 쓰는 알림 주소 방식을 따른다 · 로그인 안 된 분은 로그인 화면).
- ⚠️ 저녁 알림(`push_evening.sql`·`EVENING_LIVE`)은 다른 세션의 일 — 손대지 않는다. 크론·푸시 규칙은 `docs/notes/` 의 푸시 관련 노트와 `push_cron*.sql` 을 먼저 읽는다.

## B. 교인명부 「🎓 교육」 탭 (교회 어드민)

- 교인명부 「자세히」 창의 사역·성경필사 탭과 **같은 규칙**(설계 `docs/superpowers/specs/2026-10-01-person-history-tabs-design.md`): 그분의 교육 기록 = 그분과 이어진 앱 계정의 신청 + `ident_key = 'person|<교인ID>'`(명부에서 대신 등록한 줄).
- 줄: 학기 · 과정 · 상태(신청·확정·대기·취소·반려) · 출석률(지각=출석·공결 뺌 · `eduAttendRate`) · 수료번호(취소된 수료는 「취소됨」).
- 보는 사람: 그 창을 열 수 있는 사람(교인명부 역할) — 칸 지도 규칙 그대로(`user_id`·메모·`ident_key` 안 싣는다).

## C. 📊 교육 통계 (교회 어드민)

- 메뉴 「📊 교육 통계」(묶음 교육 · 역할 `education` 총괄만).
- 학기 고르기(전체 포함) → 강좌마다: 신청·확정·대기·취소·반려 수 · 평균 출석률 · 수료 수 · 수료율 · 그 학기 합계.
- 교구별: 확정·수료 수(교구/교회학교 부서 단위 · 목장까지는 내리지 않는다).
- 수는 **SQL 함수 하나(`edu_stats(p_term text)`)** 가 묶어서 낸다(1,000줄 함정) · 엑셀 내려받기.

## 시험·반영

- 알림: 개발에서 시험 계정 기기 없이도 `push_log`·`edu_notify_log` 로 「보냄」 확인 · 같은 알림 두 번 안 감 · 서비스 키 없이 부르면 `unauthorized` · 개강 전날 대상 고르기(내일 · 확정 · 앱 계정 · 로그 없음).
- 탭: 명부 줄 → 이어진 앱 계정 신청 + `person|ID` 신청이 함께 보임 · 남의 것 안 보임.
- 통계: 수가 줄을 직접 센 값과 같다(개발 SQL 시험).
- 운영: v2 SQL(`edu.sql` · 크론은 개발 확인 뒤) → 교회 어드민 함수 → 화면 → v2 api → bump.
