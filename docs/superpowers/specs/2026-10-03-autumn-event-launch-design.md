### 측정 시작일 SQL — `supabase/event_autumn_2026_move.sql`
- `update public.events set needs = jsonb_set(needs, '{eligibility,start}', '"2026-10-18"') where id = 'autumn-2026' and status = 'draft'`
- **막는 조건 둘을 SQL 안에 넣는다:** `status = 'draft'` 일 때만 · `event_signups` 에 이 회차 행이 **0건**일 때만(규칙을 바꾸면 과거 판정이 소급해 바뀐다 — 9/23 설계 §13 「규칙을 나중에 바꾸지 않는다」).
- 확인 질의를 같이 둔다: `needs->'eligibility'` · `opens_on > eligibility.start` (앞서면 화면이 「곧 시작」이라 하면서 신청 단추가 열린다 — 9/23 설계 SQL 주석).
- 개발 먼저 돌리고 확인 → 운영. `db query --linked` 를 쓸 때는 **어느 쪽에 이어져 있는지 먼저**(메모 `supabase-sql-needs-user`).

### 순서
날짜 칸끼리 서로를 검사한다 — 교회 어드민 `checkEvent` 는 `opens_on < eligibility.start` 면 `before-eligibility` 로 막는다.
새 값(신청 11/3 > 시작 10/18)은 어느 순서로 넣어도 걸리지 않는다. 그래도 **SQL(시작일) 먼저 → 어드민(이름·날짜)** 으로 한다.

## 8. 바뀜 (2026-10-03 같은 날 · 친구 결정) — 「하루 3번」 규칙 + 시험 참여자 시험

### 8-1. 규칙
| 항목 | 값 |
|---|---|
| 하루 한 칸 | 그날 활동 **`perDay`(=3) 번 이상**이면 한 칸 — 예전 「하루 한 번이라도」(9/23 설계 §3 「하루 ●」)를 바꾼다 |
| 「한 번」 | 앱 첫 화면 **「오늘 N회」와 같은 수** = `daily_activity.cnt` 를 모드 구분 없이 더한 값(암송 단계 하나 · 도전 한 구절 · 복습 한 구절마다 1) |
| 숫자의 자리 | `needs.eligibility.perDay` 하나. 없으면 1(다른 회차·옛 판과 맞춘다) |
| 바꿀 수 있는 때 | **10/18 개시 전까지만**(3 ↔ 5). 연 뒤에는 바꾸지 않는다(지난 날 도장이 소급해 사라진다). **인쇄물 때문에 실제 마감은 10/14** |
| 나머지 | 주 3일 · 6주 가운데 3주 · 처음 오신 분 완화 · ✨ 그대로 |
| `first_day` | 처음 오신 분 판정은 **여전히 「아무 활동이든 처음 한 날」**(문턱과 무관) |

**화면:** 도장판의 날 칸은 `n ≥ perDay` 일 때만 찍히고, 모자란 날은 「n/3」, 오늘 칸은 「오늘 n/3」으로 그 자리에서 오른다(`bumpStampToday` 는 칸을 뒤집지 않고 오늘 수를 하나 올린다). 앱 안 문구는 숫자를 박지 않고 `perDay` 를 따른다.
**바뀌는 자리:** `v2_event_weeks`(새 인자 `p_per_day` · 기본 1) · api `evtRule`·`evtStampsFor`·`eventSignup`·명단 집계 · `js/events.js`·`app.js`(알약·오늘 칸) · `events.copy.intro` · `event_streak_metrics.sql` · 포스터·공지(「하루 한 번」 → 「하루 3번」).
⚠️ **교회 어드민 가지 `autumn-excuse`(다른 세션 · 아직 main 에 안 합침)** 의 `events-elig.ts`·`index.ts` 도 `v2_event_weeks` 를 부르고 `perWeek` 로 주를 센다 — **`perDay` 를 넘겨야 명단 자격이 앱과 같아진다.** 그 세션에 알린다.

### 8-2. 시험 — 운영에서 「🧪 시험 참여자」만
- 시험 회차 **`autumn-2026-test`**: `status draft` · `needs.testOnly = true` · 제목 「[시험] 가을 말씀암송 동행」 · 측정 **2026-09-27(일)부터 6주** · `perDay 3` · **`perWeek 1` · `need 1` · `minNeed 1`**(며칠 안에 신청까지 해 보려고) · 신청 **10/4 ~ 10/17** · 목록 끝 10/17.
- 보이는 사람: 교회 어드민 ⚙️ 시스템 → 🧪 시험 참여자(app_config `ministryTesters` · api `ministryIsTester`)에 든 계정만. 다른 성도님께는 목록·도장·신청·명단 어디에도 안 나온다.
- ⚠️ `testOnly` 가 없는 draft(진짜 `autumn-2026`)는 시험 참여자에게도 **안** 보인다 — 개시 전에 진짜 회차가 새면 안 된다.
- **10/17 에 시험 회차를 지운다**(`event_signups` 는 cascade 로 함께 지워진다) → 10/18 진짜 회차 개시.

### 8-3. 일정
시험 준비 ~10/6 → 친구 시험 10/7~10/13 → **3 이냐 5 냐 확정 10/14**(주보·포스터) → 10/17 시험 회차 삭제 → 10/18 개시.

## 9. 바뀜 (2026-10-03 같은 날 · 친구 결정) — **신청 없이 「자동 대상」**

친구: 「그냥 자동으로 가면 안될까요? … 교인들은 좋아할 것 같습니다.」 영향 분석은 `.superpowers/sdd/auto-eligibility-impact-2026-10-03.md`(작업 트리 · 커밋 안 함).

### 9-1. 정해진 것
| 항목 | 값 |
|---|---|
| 신청 | **없다.** 필요한 주(세 주 · 늦게 오신 분은 `minNeed` 규칙)를 채우면 그것으로 선물 대상이다. 신청 단추·「이렇게 등록됩니다」·취소 없음 |
| 공개 명단 | **측정 기간에는 없다.** 이름은 담당자만 본다(교회 어드민). **끝나면** 선물 대상 명단(이름·소속)을 게시판이나 첫 화면에 올린다(친구 · e5 경유 2026-10-03 · 방식 미정) — 그래서 방침·앱 안내에 미리 적는다(9-4 · 플레이 심사 뒤) |
| 원하지 않는 분 | 빠지는 길을 **두지 않는다**(채우신 분은 모두 드린다) |
| 알림 | 10/18 개시 한 번. **11/3 「신청 열림」 알림은 보내지 않는다** |
| 선물 문구 | 「소정의 선물을 드려요」만. **받는 날·곳·방법은 쓰지 않는다**(친구가 그때 정한다) |
| 표시 | `events.needs.auto = true` — `autumn-2026`·`autumn-2026-test` 둘 다. SQL 로만 넣는다(교회 어드민 `EV_EDIT_KEYS` 에 `needs` 가 없어 어드민 저장에 지워지지 않는다) |
| 날짜 칸 | `opens_on`·`closes_on`·`list_until` 은 **그대로**(11/3·12/5·12/20). 성도님 화면에서는 「신청」 날짜로 쓰지 않는다. `list_until` 은 첫 화면 단추가 사라지는 날 그대로. 교회 어드민 쪽 쓰임은 e5 가 맞춘다 |

### 9-2. 성도님 화면 (`needs.auto` 회차)
- 도장판·「오늘 n/3」·7일 띠·주 칸은 **그대로**.
- 끝 문구: 대상(서버 `eligible` **또는** 그 회차에 내 줄이 있음 = 담당자가 인정해 넣은 분) → 「**선물 대상이에요 ✓** — 따로 신청하지 않으셔도 돼요」(6주 다 채운 분 ✨ 그대로) · 닿을 수 있음 → 「N 주가 되면 선물 대상이 돼요」 · 못 닿음 → 「이번엔 여기까지예요 …」 · 측정이 끝난 뒤(11/29~) → 감사 인사(대상이면 「선물 대상이에요 ✓」 유지).
- 첫 화면 단추에 「등록」이 붙지 않는다(서버 `canSignup` false).
- 「자격」·「달성」·「당첨」·「상」·「순위」·「1등」을 쓰지 않는다. 「신청」도 쓰지 않는다.

**바뀜 (2026-10-04 · 친구가 시험 회차 도장판을 보고):** 「**선물 대상이라는 용어는 빼주세요. 선물이 목적으로 보여요.** "두 주를 채웠어요" 보다는 **이벤트 기간에 참여 일을 보여 주고 앞으로 몇 일을 더 참여해야 하는지 응원의 메시지**를 주세요.」 → 위 끝 문구(과 9-6 의 「선물 대상이에요 ✓」)를 이렇게 바꿨다(`js/events.js` 순수 함수 `evtAutoWeekDays`·`evtDaysToGo`·`evtAutoHead`·`evtAutoTail` · 시험 `tests/event-auto.test.cjs`). **머리**는 「{이름} 님의 도장판 · 지금까지 N일 함께하셨어요」(0일이면 「첫 칸을 기다리고 있어요」). **N(함께한 날)** = 도장이 찍힌 날(그날 합 ≥ perDay)을 측정 기간 전체로 더한 수 — 서버 `weekDays` 에 첫 화면 알약과 같은 「오늘 살아 있는 +1」을 얹은 **배열 하나**를 주 칸·머리·끝 문구가 함께 본다(자동 대상 회차만 · 다른 회차의 주 칸은 예전 그대로 서버 값). **D(앞으로 며칠)** = 기준(사람마다 `s.need` 주 · 한 주 perWeek 일)에 닿는 가장 적은 날 수(이번 주를 남은 날 안에 채울 수 있으면 이번 주 모자란 날 + perWeek × (남은 필요 주 − 1), 아니면 다음 주부터 perWeek × 남은 필요 주, 남은 주로 못 닿으면 없음). **끝 문구** — 닿을 수 있음: 「이벤트 기간에 N일 함께하셨어요. **앞으로 D일 더** 함께하시면 돼요(한 주에 perWeek일씩).」(+ 「이번 주는 X일 더 하시면 채워져요.」 + 「오늘도 말씀과 함께 힘내요 🙂」 · 0일이면 「앞으로 D일 함께하시면 돼요(…) — 오늘 perDay번이면 첫 칸이에요.」) · 채움(서버 eligible, 또는 오늘 +1 로 닿음): 「…N일 함께하셨어요. 필요한 날을 모두 채우셨어요 🙂 남은 날도 편한 만큼 말씀과 함께해요.」(모든 주면 「✨ 매주 빠짐없이 함께하셨어요.」) · 담당자가 넣은 줄만: 「…N일 함께하셨어요. 함께해 주셔서 고마워요 — 남은 날도 편한 만큼 말씀과 함께해요.」(채웠다고 하지 않는다) · 못 닿음: 「…N일 함께하셨어요. 한 걸음 한 걸음이 귀해요 — 남은 날도 말씀과 함께해요.」 · 측정이 끝난 뒤: 「…N일 함께하셨어요. (채우신 분만 「필요한 날을 모두 채우셨어요 🙂」) 여섯 주 동안 함께해 주셔서 고맙습니다.」(✨ 유지). 머리·끝 문구에 「선물」·「대상이에요」·「N 주를 채우셨어요」·「여기까지」를 더 쓰지 않는다(안내 `copy.intro` 의 「소정의 선물」 한 줄은 그대로). 360px 에서 「지금까지 1 / 일」처럼 숫자와 「일」이 갈라져, 자동 대상 상자에만 `ev-auto` 를 붙여 머리·끝 문구를 낱말 단위로 접는다(`style.css` · 다른 회차 상자는 그대로). 부제는 「여섯 주 가운데 세 주, 말씀과 함께 걸어요」(`event_autumn_2026_perday.sql` · 옛 글자일 때만), 시험 회차 안내는 「여섯 주 가운데 한 주를 채워 참여하신 분께는 모두 소정의 선물을 드려요 — 따로 신청하지 않으셔도 돼요.」(`event_autumn_2026_test.sql`). **덧(같은 날 검토):** 이번 주만 채우면 끝나는 분은 「앞으로 D일(한 주에 3일씩)」 대신 「**이번 주에 D일 (더)** 함께하시면 돼요」(이번 주에 한 날이라도 있을 때만 「더」) · 이번 주 줄은 이번 주에 아직 한 날도 없으면 「이번 주는 3일이면 채워져요」.

### 9-3. 서버 (`api`)
- `needs.auto` 회차: `evtOpenFor` = false(목록의 `canSignup`·`verb` 「등록」 없음) · `eventSignup`/`eventDrop` 은 성도님 호출을 거절(새 오류 `auto-event` — 화면 문구 「따로 신청하지 않으셔도 돼요」) · `eventRosterPublic` 은 **빈 명단**(이름 0줄 · 시험 회차의 not-found 규칙은 그대로) · `eventStamps` 그대로.
- 다른 회차(`needs.auto` 없음)는 지금과 **똑같이** 돈다.

### 9-4. 개인정보 방침 — ⏸ **안드로이드(플레이) 심사가 끝난 뒤에** 넣는다
친구(2026-10-03): 「지금 안드로이드 심사 중이고 이 이벤트는 그 이후에 예정되어 있습니다. **공지나 개인정보 방침에는 당장 기록하지 마세요.**」
→ Task 15 에서 넣었던 방침 세 곳(웹 `privacy/index.html` 표·4항 · 앱 `renderPrivacyInfo`·`renderHelp`)은 **되돌렸다**(운영에 나간 적 없음).
**심사 통과 뒤 · 10/18 측정 시작 전**에 아래를 넣는다(웹·앱 안 화면 **같은 커밋** · 「마지막 수정」 날짜):
- 친구 결정(e5 경유 2026-10-03): 「행사가 끝나면 선물 대상 명단을 게시판에 올리거나 썸머 써바이블처럼 첫 화면에 올린다」 · 「선물은 따로 묻지 않는다」.
- 방침 문장: 「**신청 없이 암송 기록으로 세는 이벤트**도 있습니다 — 측정 기간에는 이름·소속을 담당자만 보고, 행사가 끝나면 **기준을 채우신 분의 이름·소속을 그 이벤트 명단에 남기고(신청하지 않으셔도), 그 명단(이름·소속)을 게시판이나 앱 첫 화면에 올립니다**(몇 주를 채웠는지·인정 사유는 올리지 않습니다).」
- 앱 안내(`copy.intro` 끝 한 줄 · `event_autumn_2026_perday.sql`): 「행사가 끝나면 선물 대상 명단(이름·소속)을 게시판이나 첫 화면에 올려요.」 — 이것도 심사 뒤에(친구: 「방침 + 앱 안내 한 줄」).
- 끝난 뒤 첫 화면에 올리기로 하면 `eventRosterPublic` 의 auto 갈래가 빈 명단 대신 **도장 셈 + 인정 줄로 만든 명단**을 내야 한다(11/28 측정 끝·명단 확정 뒤 공개 · 게시판이냐 첫 화면이냐는 아직 안 정함).

### 9-5. 교회 어드민 (e5 · autumn-excuse 가지)
선물 명단 = **대상 전원**(주로 채운 분 + 인정한 분) · 교구·목장별 · CSV · 기간 뒤에도 이름이 보이게. 인정은 지금처럼 `event_signups` 줄로. 명단 확정(11/29 무렵) 전에 계정이 갈린 분을 잇는다. **2026-10-03 e5 에 알림.**

### 9-6. 시험 회차
`autumn-2026-test` 에도 `needs.auto = true` — 시험 참여자가 10/7~10/13 에 「선물 대상이에요 ✓」를 직접 본다(need 1 이라 9/27 이후 하루라도 3번 하신 분은 곧바로 대상). 시험 신청은 아직 0건이라 지울 것이 없다.

### 9-7. 배포 순서
**api → 프런트(bump·push) → 자료 SQL(`needs.auto`·안내 문구)**. 자료를 먼저 넣으면 옛 화면이 신청 폼을 그리는데 서버만 거절한다 — 진짜 회차는 draft 라 시험 참여자에게만 생기는 일이지만 순서를 지킨다.
