# 가을 말씀 동행 — 꾸준히 하신 분께 드리는 이벤트 (설계)

> 작성 2026-09-23 · 저장소 `bible-memorize-church-app-v2` (gocheok.onlybible.kr)
> 이 문서만 읽고 구현할 수 있게 적었다. 대화 맥락을 몰라도 된다.

**한 줄.** 6주 동안 **한 주에 3일씩 3주를 채우신 분**께 선물을 드린다.
자격은 서버가 세고, 채워지면 **신청 단추가 열린다.** 상은 **신청하신 분 모두 같은 것** 하나다.

---

## 1. 왜 이걸 만드나

`docs/analysis/2026-09-23-usage-analysis.md` 가 두 가지를 말한다.

- **9/30 에 「말씀암송이 답이다!」가 끝난다.** 그 뒤에 유입이 아니라 이탈만 남는다.
- **상위 10명이 전체 반복의 67.7%**를 차지한다. 그래서 **「몇 번 했나」로 줄을 세우면 안 된다** —
  1등은 시작 전에 정해져 있고 나머지는 응모조차 안 한다.

그래서 **횟수가 아니라 꾸준함**을 재고, **순위가 아니라 문턱**으로 연다. 겨루는 이벤트가 아니다.

## 2. 정해진 것

| 항목 | 값 | 누가 정했나 |
|---|---|---|
| 이름 | **가을 말씀 동행** (`title` 「2026 가을 말씀 동행」 · `short_title` 「가을 말씀 동행」) | 친구 |
| 목적 | 꾸준히 하신 분께 선물 (겨루기·추첨 아님) | 친구 |
| 잣대 | **주 단위** (횟수·구절 수 아님) | 친구 |
| 측정 창 | **2026-10-11(주일) ~ 11-21(토)**, 6주 = 42일 | 친구 (「날짜는 유동적, 우선 10/12」 → 10/11 주일로 하루 당김) |
| 문턱 | **주 3일 × 3주** (6주 가운데) | 친구 |
| 중간에 처음 오신 분 | 남은 주로 분모를 줄인다 | 친구 |
| 사정 보정 | 담당자가 인정할 수 있게 만든다 (사유를 남긴다) | 친구 |
| 시상 | **신청하신 분 모두 같은 것.** 등급 없음 | 친구 |
| 진행 표시 | 첫 화면 이벤트 단추 + 이벤트 화면 도장판 | 친구 |
| 구현 | 기존 이벤트 플랫폼(`events`/`event_signups`)에 「자격」한 겹 | — |

### 왜 주일에 시작하나
`verses.date` 가 **토(23건)·금(11건)**에 몰려 있다 — 새 구절을 주말 직전에 올려 **주일부터** 쓰게 한다.
이벤트 주를 월~일로 잡으면 **주일에 하신 암송이 「지난 주」 칸에 찍힌다.** 주보도 주일에 나온다.
⚠️ **Postgres `date_trunc('week')` 는 월요일 시작이다.** 쓰지 말 것 — `floor((day - start)/7)` 로만 센다.
⚠️ 날짜를 옮길 때는 **7일 단위로만** 옮긴다. 다른 요일로 가면 화면에서 「이번 주」라는 말을 빼고 날짜로 말해야 한다.

## 3. 규칙

```
측정 창   2026-10-11(일) ~ 2026-11-21(토) · 6주
  1주 10/11~10/17   2주 10/18~10/24   3주 10/25~10/31
  4주 11/01~11/07   5주 11/08~11/14   6주 11/15~11/21

하루 ●   그날 daily_activity 에 그 사람 기록이 있으면 한 칸
주   ✓   한 주에 3일 이상이면 그 주 채움
자격     채운 주가 필요 주수 이상 → 신청 단추가 열린다
필요 주수  기존에 쓰시던 분        3주
           이벤트 중 처음 오신 분   max(2, floor(남은 주 / 2))
✨       6주를 다 채우면 본인 화면·담당자 명단에만 ✨ (상은 같다)
```

⚠️ **✨ 는 「6주 모두」다 — 필요 주수를 넘긴 것이 아니다.** 그러니 중간에 오신 분은 ✨ 를 받을 수 없다.
그래도 그대로 둔다: ✨ 에는 **선물이 걸려 있지 않고**, 기준을 사람마다 다르게 하면 「저분 ✨ 는 무슨 뜻이냐」가 된다.
✨ 는 공개 명단에 안 나가므로(§10) 남과 견줄 자리도 없다.

### 「이벤트 중 처음 오신 분」의 정의
`firstDay` = 그 사람의 **가장 이른 `daily_activity.day`** (이벤트 이전까지 통틀어).

- `firstDay < 2026-10-11` → 기존에 쓰시던 분 → **필요 3주** (완화 없음)
- `firstDay >= 2026-10-11` → 그 주부터 남은 주 수 `R` → **필요 `max(2, floor(R/2))`**

| 처음 오신 주 | R | 필요 |
|---|---:|---:|
| 1주 | 6 | 3 |
| 2주 | 5 | 2 |
| 3주 | 4 | 2 |
| 4주 | 3 | 2 |
| 5주 | 2 | 2 |
| 6주 | 1 | 2 → **닿을 수 없다** |

⚠️ **`firstDay` 를 이벤트 안에서 보면 안 된다.** 「이벤트 기간 중 첫 활동」으로 재면
**기존 회원이 일부러 늦게 시작해 문턱을 낮출 수 있다**(먼저 시작한 분이 손해를 본다).
전 기간에서 재야 「처음 여신 분」이라는 말과 실제가 맞는다.
로그인만 하고 활동이 0이던 191명은 `daily_activity` 에 행이 없으므로 저절로 「처음 오신 분」이 된다 — 의도한 것이다.

### 근거 숫자 (운영 DB · 2026-09-23 실측)
`2026-08-09(주일)~09-19(토)` 꼭 6주에 이 규칙을 그대로 적용한 값이다.

| 채운 주 | 인원 |
|---|---:|
| 활동한 분 | 185 |
| 1주 이상 | 83 |
| 2주 이상 | 58 |
| **3주 이상 ← 문턱** | **40** |
| 4주 이상 | 16 |
| 6주 모두 | 6 |

⚠️ 이 창은 「말씀암송이 답이다!」(8/16~9/30)가 도는 중이라 **이미 이벤트 효과가 섞여 있다.**

**평시 기준선(2026-09-23 실측).** 이벤트 전 6주 `2026-07-05(주일)~08-15(토)` 를 같은 규칙으로 재면:

| 창 | 활동한 분 | 3주 이상 |
|---|---:|---:|
| **평시 7/05~8/15** (이벤트 전) | **66** | **12** |
| 이벤트 중 8/09~9/19 | 185 | 40 |

**읽는 법.** 평시에 이 문턱을 넘는 분은 **12명**이다. 이벤트가 도는 동안 **40명**이 됐고,
활동자 자체가 **66 → 185명으로 세 배**가 됐다. 그러니 이번 회차의 기대치는 12명이 아니라
그 사이 어딘가다 — **이벤트가 사람을 데려온다는 증거**이기도 하다.
질의는 `supabase/event_streak_metrics.sql` 에 고정해 두었다(§9).

## 4. 날짜를 두 쌍으로 가른다 ⚠️

| 무엇 | 언제 | 어디에 적나 |
|---|---|---|
| **측정 창** | 2026-10-11 ~ 11-21 | `needs.eligibility.start` + `weeks` |
| **신청 창** | `opens_on` **2026-10-27** ~ `closes_on` **2026-11-28** | `events` 표 |
| 명단 공개 종료 | `list_until` **2026-12-13** | `events` 표 |

**왜 가르나.** 3주가 **가장 빨리 성립하는 날이 10/27(화)**이다(1·2·3주에 3일씩).
그전에 신청을 열어 두면 화면이 16일 동안 「등록하세요」라고 거짓말한다 —
`canSignup` 이 true 면 첫 화면이 「등록」을 붙이고(js/events.js:198-199), 목록 정렬이 그 회차를 맨 위에 못 박는다.
가른 덕에 **마지막 주 마지막 날에 자격이 된 분이 그날 밤 안에 눌러야 하는 문제**도 사라진다(11/28 까지 받는다).

⚠️ `list_until` 을 **반드시 채운다.** 비우면 `evtListable` 이 기한 없이 계속 보여 줘서
「6주 중 3주」가 12월에도 첫 화면에 박혀 있다(index.ts:4754-4758).

⚠️ **개시 전에 `summer-2026` 의 `list_until` 을 박거나 내린다.** 회차가 둘이면 첫 화면 라벨이
「이벤트 2개」로 접혀(app.js:365) 진행 줄의 주인이 사라진다.

## 5. 무엇을 세는가 — **mode 를 나열하지 않는다** ⚠️ 치명

**「그날 `daily_activity` 에 그 (day, user_id) 행이 있는가」로만 본다.** mode 를 열거하면 안 된다.

`challenge_log.mode` CHECK 는 **여덟 가지**다 — `supabase/migrate_modes_card.sql:42-43` 에
`learn-typing-card`(암송 카드)·`typing-card`(도전 카드)가 더 있다. 그 둘이 곁가지가 아니다:

| mode | 반복 | 비중 |
|---|---:|---:|
| `learn-typing-card` | 48,715 | **39.4%** |
| `typing-card` | 31,994 | **25.8%** |

(`docs/analysis/2026-09-23-usage-analysis.md:186-193` · 카드가 암송의 59.6%·도전의 77.5%다)

여섯 개만 세면 **카드로만 하시는 분은 매일 하셨는데 도장이 하나도 안 찍힌다.**
`v2_mydays` 가 이미 mode 를 안 가리고 `sum(cnt)` 한다(`supabase/daily-activity.sql:145-155`) — 그 잣대를 따른다.

**대가.** 규칙에 안 적은 활동도 도장을 찍는다 — 쉴만한 물가·「내 안에 거하는 말씀」·영어 모드가 전부 들어온다.
그래서 **문구를 「앱에서 말씀과 함께하신 날」로 넓혀 쓰고, 조건 문장에 기능 이름을 나열하지 않는다.**
좁히려면 `challenge_log.verse_no` 를 봐야 하는데 그것은 집계표를 우회하는 질의라 순위·mydays 와 숫자가 갈린다(CLAUDE.md 경고). 좁힐 이유가 없다.

⚠️ `needs.eligibility` 에 mode 목록을 **넣지 않는다.** 넣으면 허용 목록이 DB CHECK·서버·jsonb 세 곳으로 갈라진다.

⚠️ **목록은 늘어나는 중이다 — 이 결정이 옳았다는 증거가 같은 날 나왔다.**
이 문서를 쓴 2026-09-23 당일, 다른 작업이 **아홉 번째 값 `review-typing-card`** 를 저장소에 넣었다
(`supabase/migrate_modes_review_card.sql` · 커밋 `9378424`). 운영 CHECK 에는 아직 여덟뿐이라
**저장소와 운영이 서로 다른 상태**다. 자격 계산이 mode 를 열거했다면 그날 조용히 틀어졌을 것이다.

## 6. 서버

### 6.1 자격 규칙은 `events.needs.eligibility` 에

```json
{ "eligibility": { "start": "2026-10-11", "weeks": 6, "perWeek": 3, "need": 3, "minNeed": 2 } }
```

`kind` 는 **`signup` 그대로** 둔다 — `events_kind_chk` 를 안 건드린다(허용 목록이 세 곳으로 갈라지는 자리).
화면도 `kind` 로 분기하지 않는다.

### 6.2 새 액션 `eventStamps` — eventOpenList 에 얹지 않는다 ⚠️

`eventOpenList` 는 매 부팅에 불리고(app.js:123 → 345) **일부러 `user_id` 를 안 보낸다**(app.js:347-348 주석 — 「여기서 필요한 것은 『볼 회차가 있는가』 하나뿐이다」).
응답 모양을 첫 화면 게이트·이벤트 카드·관리자 미리보기 셋이 함께 쓴다. 새 액션으로 뺀다.

```
eventStamps { user_id, event_id }
  → { ok:true,
      rule:   {start, weeks, perWeek, need} | null,   // null 이면 자격 회차가 아니다
      phase:  "before" | "measuring" | "signup" | "over",
      days:   ["2026-10-11", …],   // 채운 날
      weekDays: [3,2,0,1,3,0],     // 주별 채운 날 수
      weeksDone: 3,
      need: 3,                     // 이분에게 필요한 주 수(중간 합류 반영)
      eligible: true,
      allSix: false,
      canStillReach: true }
```

- **`phase` 를 서버가 정한다.** `canSignup` 불리언으로는 「측정 중」을 표현할 수 없다.
  화면이 날짜를 다시 재면 서버와 갈라진다(`verb` 를 서버가 정하는 것과 같은 까닭, js/events.js:198-199).

  | `phase` | 언제 | 화면 |
  |---|---|---|
  | `before` | `today < start` (~10/10) | 「10월 11일에 시작해요」 |
  | `measuring` | `start ≤ today < opens_on` (10/11~10/26) | 도장판 · 단추 자리에 말 |
  | `signup` | `opens_on ≤ today ≤ closes_on` (10/27~11/28) | 도장판 + 자격이 되면 신청 단추 |
  | `over` | `today > closes_on` (11/29~) | 「함께한 기록 보기」 · 명단 |

  ⚠️ 10/27~11/21 은 **측정과 신청이 겹친다.** 그때는 `signup` 이다 —
  화면이 달라지는 것은 「단추가 열리느냐」이기 때문이다. 측정이 끝났는지는 도장판이 다 찬 것으로 보인다.
- **`canStillReach` 를 서버가 싣는다.** 남은 주를 다 채워도 못 닿는 분께 「세 주가 되면 열려요」를
  계속 띄우면 헛수고를 권하는 것이고, 마감 화면에서 처음 알게 되면 그게 「떨어졌다」가 된다.
- ⚠️ **진행률은 `user_id` 로만 조회받는다.** 이름·구분·소속 네 조각으로 지목하는 응원 패턴
  (`docs/notes/ranking-cheer.md`)을 복사하면, 공개 명단을 입력으로 **전 교인의 42일 활동표를 긁을 수 있다.**

### 6.3 주차 집계는 RPC 안에서 끝낸다 ⚠️

PostgREST 로 여러 사람 주차를 세면 안 된다 — 한 번에 **1000행 상한**이라 이걸 모르면 **조용히 잘린 값**이 나온다
(index.ts:2182-2183 — 그래서 통계 쪽은 1000행씩 이어 받는다). 게다가 `.in("user_id", […])` 는
사람이 늘수록 주소가 길어져 한도에 걸린다.
`group by`·`count(distinct)` 는 애초에 안 된다.

```sql
-- supabase/event_stamp_2026.sql 에 함께 둔다
create or replace function v2_event_weeks(p_start date, p_weeks int, p_per_week int, p_users text[] default null)
returns table(user_id text, week_no int, days int) …
create index if not exists daily_activity_user_day_idx on public.daily_activity (user_id, day);
```

- `floor((d.day - p_start)/7)` · `d.day between p_start and p_start + (p_weeks*7 - 1)`
- **반환에 이름·소속을 넣지 않는다.**
- ⚠️ 파일 끝에 `revoke all on function … from public, anon, authenticated` +
  `grant execute … to service_role` 를 **반드시** 붙이고, `proacl` 확인 질의로 「anon 열림 0건」을 눈으로 본다.
  본보기는 `supabase/daily-activity.sql:169-176`. **2026-09-23 에 `stats-rpc-card.sql` 이 이걸 빠뜨려
  성도님 실명·교구·목장이 공개 키로 나갔다**(`supabase/security_close_stats_rpc.sql`).
- `drop function` 을 쓰지 않는다 — `create or replace` 는 ACL 을 지킨다.
- 인덱스가 필요한 이유: PK 는 `(day,user_id,mode)` 이고 별도 인덱스는 `(day)` 뿐이다
  (`supabase/daily-activity.sql:25-27`). `v2_mydays` 도 함께 빨라진다.

### 6.4 날짜는 `evtToday()` 만 쓴다 ⚠️
`ymd()` 는 UTC 라 KST 0~9시에 하루가 어긋난다(아침 알림 `latestVerse` 가 같은 버그다).
`daily_activity.day` 는 이미 KST 다(`supabase/daily-activity.sql:38-40`).
`challenge_log` 폴백을 만들지 않는다 — 숫자가 조용히 갈린다.

### 6.5 `eventSignup` 에 재검사를 넣는다 ⚠️

지금은 기간(`evtOpenNow`)과 `needs.position/phone/memo` 만 본다. **화면이 잠겨 있어도 액션은 열려 있다.**
JWT 가 없어(`--no-verify-jwt`) 누구나 직접 부를 수 있다.

- `needs.eligibility` 가 있으면 **서버가 다시 세서** 미달이면 `not-eligible` 로 막는다.
- ⚠️ **클라이언트가 보낸 `answers` 를 저장하지 않는다.** 지금은 객체이기만 하면 그대로 넣는다
  (index.ts:4908-4909 → 4922) — 누구나 `weeks:[1,1,1,1,1,1]` 을 보낼 수 있다.
  자격 회차에서는 `b.answers` 를 **읽지 않고** 서버가 센 값만 넣는다
  (키 화이트리스트 `weeks`·`days`·`rule`·`computed_at`, JSON 2KB 상한).
- 거절 슬러그를 세 갈래로 고친다 — `today < opens_on` 이면 **`not-yet`**.
  지금은 `status` 가 open 인데 아직 안 열렸어도 「마감했어요」라고 답한다(index.ts:4885).

### 6.6 ✨ 는 **종료 뒤 재계산**으로 정한다 ⚠️

응모 시점 스냅샷으로는 맞힐 수 없다 — 10/27 에 신청한 분의 스냅샷은 3주로 굳고, 그 뒤 세 주를 더 채워도 안 바뀐다.
**일찍 신청한 분이 벌을 받는다.**

- 스냅샷(`event_signups.answers`)은 **「그때 이 기준으로 열어 줬다」는 증빙**으로만 쓴다.
- 자격·✨ 는 **뽑는 시점에 서버가 다시 센다.** 담당자 화면에 「최종 집계」 단추 하나.
- **기간 중에는 ✨ 를 아무 화면에도 안 보여 준다**(그래야 말이 맞는다).

### 6.7 담당자용

- `eventRoster` rows 에 **파생값만** 더한다 — `weeksDone`·`perfect`·`eligible`·`signedUp`·`computedAt`.
  **`answers` 원본은 내보내지 않는다.**
- 보정 액션 둘: `eventSetNote`(사유) · `eventOverride`(인정/보류 + 사유 → `answers.excuse` 에 주 번호).
  ⚠️ 보정은 **`event_signups` 쪽에만** 쓴다. `challenge_log`·`daily_activity` 를 손대면
  순위·통계·주간 리포트가 함께 오염된다.
- ⚠️ `event_signups.note` 는 서버가 읽기만 하고 **쓰는 액션도 화면도 없다** — 이번에 만든다.
- **「자격은 되는데 아직 신청 안 하신 분」** 목록을 만든다(이름·소속·목장만, **`user_id` 금지**).
  썸머 때 등록 200명 중 앱 계정이 79명이었다 — 자격자가 전부 단추를 누르지는 않는다.

  (index.ts:4969-4970 의 select 목록). 바로 위 4966-4968 에 그 까닭이 적혀 있다 —
  「고칠 수 있는 칸은 빠짐없이 돌려줘야 한다. 하나라도 빠지면 그 칸이 빈 채로 그려지고,
  **저장하는 순간 원래 값이 지워진다**」. 폼을 만들면 규칙을 지우는 쪽이 먼저 온다.

  **보낸 칸만 바꾼다**(index.ts:5036-5037 `has("needs") ? objOf(e.needs) : cur.needs`).

  `needs: cur.needs || {}` 를 실어 보내면 **자격 규칙이 조용히 지워진다** —
  오류도 안 나고 아무에게도(또는 모두에게) 단추가 열린다.

## 8. 문구

성도님 화면에서 **「응모」·「당첨」·「자격」·「미달」·「전원 시상」·「달성」·「개근」·「100%」를 쓰지 않는다.**

「당첨자 발표는 교회 안내를 확인해 주세요」(1843)다. **옛 퀴즈 완료 화면(1832-1850)을 재사용하지 않는다.**

|---|---|
| 응모 | **신청** |
| 당첨 · 전원 시상 | 「신청하신 분께는 모두 드립니다」 |
| 상 | **선물** (기념 선물) |
| 자격 | (말하지 않고 **셈만** 보여 준다) |
| 6주 중 3주 | 「3주 채웠어요 〈작게〉전체 6주〈/작게〉」 — 단위를 두 번 세지 않는다 |

### 첫 화면 단추 알약 (상태별)

| 상태 | 문구 |
|---|---|
| 시작 전 | 「10월 11일에 시작해요」 |
| 이번 주 0일 | 「이번 주 ○○○ · 오늘 한 번이면 한 칸」 |
| 1일 | 「이번 주 ●○○ · 2일만 더 채우면 돼요」 |
| 2일 | 「이번 주 ●●○ · 하루만 더 채우면 돼요」 |
| 이번 주 채움 | 「이번 주 ●●● 채웠어요 · 지금까지 2주」 |
| 신청 열림 | 「세 주를 채우셨어요 · 눌러서 신청하세요」 |

- ⚠️ 「✨이」처럼 **그림글자에 조사를 바로 붙이지 않는다** — 늘 「✨ 표가」.
- 마감 뒤에도 **단추는 살아 있어야 한다**(그 안에 명단이 있다, js/events.js:196-197).

### 도장판

- 머리: 「○○○ 님의 도장판 · 지금까지 2주 채웠어요」 + 칸마다 날짜(「1주 10/11~10/17」).
  **칸을 세게 하기 전에 답을 먼저 준다.** 채운 칸은 ● 대신 **✓**.
- 아래 작은 글씨 둘:
  - 「한 날에 여러 번 하셔도 그날 한 칸이에요.」 ← 없으면 「세 번 했으니 이번 주 다 채웠다」로 읽는 분이 반드시 나온다
  - 「인터넷이 연결된 상태에서 저장된 날만 셉니다.」

```
지금까지 2주를 채우셨어요.
세 주가 되면 이 자리에 신청 단추가 열려요.
남은 주에 3일씩만 채우시면 돼요.
```

**남은 주로 못 닿을 때** — 기준을 다시 말하지 않는다.
```
이번 신청은 여기까지예요. 채우신 2주는 그대로 남아요 — 다음에 또 함께해요.
```

### 신청 완료 (appAlert 한 줄로 끝내지 말고 화면으로)
```
신청이 끝났어요
{이름} 성도님 이름을 명단에 올렸어요.
지금까지 채우신 3주를 그대로 적어 두었어요.
남은 주도 편한 만큼 함께해요.
```
셋째 줄이 스냅샷을 성도님 말로 옮긴 것이다 — 없으면 「신청한 뒤에 한 주 쉬면 취소되나요」를 담당자에게 묻는다.

### 마감 뒤 · 못 채우신 분
```
여섯 주 동안 함께해 주셔서 고맙습니다.
{이름} 성도님은 2주를 채우셨어요. 채우신 날은 그대로 남아 있어요.
다음 걸음에 또 함께해요.
```
**첫 줄이 감사다.** 「아쉽게도」·「다음 기회에」는 탈락 통지문의 관용구라 쓰지 않는다.
이 화면에도 참여자 명단을 함께 보여 준다(자기 줄이 거기 있다).

|---|---|
| `not-eligible` | 「아직 신청이 열리지 않았어요. 여섯 주 가운데 세 주를 채우시면 열려요.」 |
| `not-yet` | 「10월 27일부터 신청을 받아요.」 |

## 9. 재는 법 — 기준선을 **공지 전에** 뜬다 ⚠️

`supabase/event_streak_metrics.sql` 을 **개시 전에** 만든다(꼴은 `supabase/challenge_funnel.sql` 그대로 —
머리에 정의와 「다시 잴 때는 이 파일을 그대로 쓴다」, 본문은 번호 붙인 독립 질의, 결과란).

기준선을 **둘** 뜬다 — §3 의 40명은 지난 이벤트 한복판에서 잰 값이라 낙관적이다.

| | 창 | 무엇 |
|---|---|---|
| A | 2026-08-31 ~ 10-11 | 직전 6주 |
| B | 2026-07-06 ~ 08-15 | 평시 6주(이벤트 전) |

- 창의 시작일은 **파일 맨 위 한 줄에서만** 바꾼다.
- `select count(*) from challenge_log` 와 `v2_activity_drift()`·공지일을 함께 적는다 —
  삭제 요청·계정 합치기가 **과거 집계를 실제로 줄인다.**
- ⚠️ **공지 전에 떠야 한다.** 지난 이벤트에서 공지 주부터 이미 올랐다(전환율 14.7 → 27.0%).
- `FEATURES` 허용 목록(`featureLog` · `supabase/feature_log.sql`)에 `event` 를 더해
  **개시일부터** 이벤트 화면 열람을 남긴다 — 나중에 켜면 그 구간이 영구히 빈다.
- ⚠️ CLAUDE.md 가 가리키는 `supabase/psalm_metrics.sql` 은 **파일이 없다.** 그 자리를 반복하지 않는다.

12월에 같은 파일로 ③(기간)·⑤(자격 vs 신청)·⑥(종료 후 4주 지속)을 다시 돌린다.

## 10. 개인정보 ⚠️

`privacy/index.html:141-147` 은 공개되는 것을 **순위·게시판·사진 셋만** 적는다 —
**이벤트 명단이 한 줄도 없다.** `privacy/` 와 앱 안 개인정보 화면 **두 곳**에
「이벤트 명단(이름·소속)이 다른 성도님께 보입니다」를 더한다. **같은 커밋에.**

- ⚠️ **공개 명단에 ✨·주차 수·도장판을 싣지 않는다.** 이번 명단은 「신청했다」가 아니라
  **「꾸준히 했다는 판정 결과」**라, 별이 없는 줄이 곧 **공개된 등급**이 된다.
  덤으로 `eventRosterPublic` 의 다섯 칸 화이트리스트(index.ts:5124 — 직접 확인함)를 안 건드려도 된다.
  ✨ 는 **본인 화면·담당자 화면·시상식 호명**에만.
- ⚠️ **응답에 `user_id` 를 싣지 않는다.** 관리자 명단은 지금 `hasUser` 만 준다(index.ts:5014) —
  주차는 **signup 행 id 에** 붙인다(`user_id` 키 맵 금지). `select("*")` 로 바꾸지 않는다.
- ⚠️ **자격이 돼도 자동으로 `event_signups` 에 넣지 않는다.** 명단이 공개되므로 동의 없이 이름이 올라간다.

## 11. 계정이 갈린 분 ⚠️

계정 합치기는 **두 계정이 같은 회차에 신청해 있으면 거부**된다
(`supabase/member_merge.sql:123` `merge-signup-conflict`)고, 관리자가 신청을 지우는 길은 없다
(`eventDrop` 은 본인·기간 안에서만).

→ 순서를 못 박는다: **합치기 → 신청.** 개시 전에 `adminPreviewMemberMerge` 로 중복 후보를 한 번 훑고,
**관리자 전용 신청 삭제**를 하나 만든다(사유를 `note` 에).

## 12. 안 하기로 한 것

| 안 하는 것 | 왜 |
|---|---|
| 요청 수 제한·사람 확인·간격 검사·같은 구절 반복 금지 | **지름길이 없다.** `challenge_log.created_at` 을 받는 앱 액션이 한 곳도 없어(DB `default now()`) 과거를 만들 수 없다. 위조는 오늘 하루뿐이고, **주3일×3주 = 9개 날짜는 실제로 9번 들러야** 생긴다. 하루에 수백 번 해도 도장은 하나라 매크로도 무의미하다 |
| 여러 계정 만들기 막기 | 비번이 없어 `login` 이 모르는 이름이면 계정을 만들어 준다. 정작 위험한 것은 **반대 방향**(한 분이 이름을 다르게 적어 9일이 5일+4일로 갈리는 것)이라, 막는 대신 도장판에 「이 계정으로 채운 날」을 **날짜로 그대로** 보여 준다 |
| 실패한 활동 재전송 큐 | `postProgress`·`postChallenge` 는 실패하면 기기에만 남기고 끝이다(app.js:908-923 · 7786-7800). 이번엔 **문구로 정직하게 적고** 담당자 보정으로 받는다. 대가: 통신이 끊긴 날이 실제로 빠진다 |
| `challenge_log` 폴백 질의 · mode 허용 목록 · `needs` 에 mode 목록 | 셋 다 집계표를 우회하거나 허용 목록을 네 곳으로 늘려 **숫자가 조용히 갈리는** 길 |
| `kind` 에 새 값 | `events_kind_chk` 를 안 건드린다. 화면도 `kind` 로 분기하지 않는다 |
| 관리 화면의 `needs` 편집 폼 | `eventRoster` 가 `needs` 를 안 돌려줘(index.ts:4969-4970) **빈 값으로 규칙을 지울** 위험이 먼저 온다. 원본은 `event_stamp_2026.sql` 한 파일 |
| 목록 정렬을 세 단계로(잠김 < 마감) | 신청 창을 10/27 로 가르며 사라진 문제. 회차가 둘이 되는 날 다시 본다 |
| 잠긴 단추를 `disabled` 로 | 어르신께 회색 단추는 「나는 안 된다」다. 자리에 말을 둔다 |
| 대리 등록(종이로 암송하신 분) | 이번엔 보정 창구로만 받는다. `eventImport` 로 넣은 줄은 서버 계산으로 늘 미달이라 따로 다뤄야 한다 |

## 13. 배포 순서 — **코드가 먼저** ⚠️

`events` 는 **이미 성도님이 읽는 표**이고 그 목록의 길이가 곧 첫 화면 단추의 게이트다(app.js:345-374).
행을 먼저 넣으면 **옛 `js/events.js` 가 도장판 없는 일반 신청 폼을 띄운다.**

0. **개시 전 확인** — 운영에서 `select id,status,opens_on,closes_on,list_until from public.events`.
   `summer-2026` 이 목록에 남으면 라벨이 「이벤트 2개」가 된다. `adminPreviewMemberMerge` 로 갈린 계정을 훑는다.
1. **기준선**(§9) — 공지 **전에** A·B 두 창을 돌려 파일 머리에 박는다.
2. **개발 DB 에 SQL** — `v2_event_weeks` + `daily_activity_user_day_idx` + revoke/grant + `proacl` 확인. `create or replace` 만.
3. **개발 DB 에 가짜 42일** — `login` 으로 네 사람(6주 전부 / 3주 딱 / 2주 미달 / 어떤 주는 2일)을 만들고
   **`challenge_log` 에 `created_at` 을 과거로** 넣어 트리거가 집계표를 채우게 한다
   (개발 DB 는 비어 있다). **mode 에 `learn-typing-card`·`typing-card` 를 일부러 섞는다.**
4. **개발 DB 에 회차 행** — `supabase/event_stamp_2026.sql` 로 `status='draft'` +
   `needs.eligibility` + `opens_on 2026-10-27` / `closes_on 2026-11-28` / `list_until 2026-12-13` + `copy`.
   여러 번 돌려도 안전하게. ⚠️ 손으로 치는 UPDATE 를 쓰지 않는다(`db query --linked` 는 운영이다).
5. **서버를 개발에만** — `deploy api --no-verify-jwt --project-ref ktpwthwqzgcqcrmsafdo`.
   변경은 **새 액션 + `eventSignup` 의 `if (needs.eligibility)` 분기 + 거절 슬러그 + `eventRoster` 파생값 + 보정 액션**으로 한정.
6. **개발에서 확인** — `v2_activity_drift()` → `mydays` 날짜별 → 새 액션의 주별 ✓ →
   **자격 없는 계정으로 `eventSignup` 을 직접 불러 서버가 거절하는지** → 자격자로 신청 →
   `answers` 가 서버 계산으로 덮였는지 → `eventRosterPublic` 에 `answers`·`user_id` 가 안 섞였는지.
7. **프런트** — `js/events.js` · `app.js` · `admin-event.html`.
   localhost 확인 → `python tools/preflight.py` 손으로 한 번 → `python tools/bump.py` → **경로를 못 박아** 커밋.
8. **`privacy/` 와 앱 안 개인정보 화면** 두 곳 — 같은 커밋에.
9. **운영 Edge Function** — ⚠️ `git status --short` 로 **남의 미커밋 코드가 없는지 보고 나서**.
   `supabase functions deploy` 는 git 이 아니라 **작업 트리**를 올린다(2026-09-10 실제 사고).
10. **운영 SQL** — RPC·인덱스 → `proacl` 로 「anon 열림 0건」을 눈으로 → `event_stamp_2026.sql` 로 회차를 **draft 로**.
11. 운영 API 를 관리자 암호로 찔러 draft 회차가 서는지 본다. **여기까지 성도님 화면은 한 번도 안 바뀐다.**
12. **2026-10-11 아침 — `admin-event.html` 에서 draft → open 한 번.**
    이것이 개시 행위다. **사람이 손으로 한다** — 계획에 할 일로 적어 두지 않으면 아무 일도 안 일어난다.
    직후 확인 둘: 첫 화면에 단추가 뜨는지 · 도장 수가 `mydays` 와 같은지.
13. **10/27** — 신청 창이 날짜로 저절로 열린다. 열린 날 목장·주보로 알린다.
14. **11/22 이후** — 담당자 화면 「최종 집계」로 자격·✨ 를 다시 세고 명단·CSV. 「자격은 됐는데 신청 안 하신 분」도 함께.
15. **12월** — `event_streak_metrics.sql` 을 다시 돌린다. `list_until`(12/13)이 지나면 단추는 저절로 사라진다.

### 노출 게이트 ⚠️
**새로 만들지 않는다 — 회차 자료 자체가 게이트다**(app.js:323-325).
그리고 **`status='open'` + 미래 `opens_on` 은 게이트가 아니다** — `evtListable` 은 `status` 만 보고
날짜를 안 본다(index.ts:4754-4758). 개시 전까지 유일한 잠금은 **`status='draft'`**.
대가: 운영에서 성도 화면 미리보기가 안 된다(`?preview=event` 는 암호를 안 보낸다) —
**화면 검수는 개발 DB 에서 끝낸다.**

### 커밋 ⚠️
`git add -A`·`git commit -a`·넓은 restore/reset/stash 금지. `app.js`·`index.ts` 처럼 남과 겹치는 파일은
임시 인덱스(`GIT_INDEX_FILE`)로 **내 헝크만** 담고 `git show --stat HEAD` 로 눈으로 본다.
`bump.py` 는 PR 에 넣지 않는다(머지 뒤 친구가 한 번).

### 규칙을 나중에 바꾸지 않는다 ⚠️
**신청이 한 건이라도 들어온 뒤에는 `start`·`weeks`·`perWeek`·`need` 를 바꾸지 않는다.**
즉석 계산이라 과거 판정까지 소급으로 바뀌어 **어제 열렸던 단추가 오늘 잠긴다.**
바꿔야 하면 **회차를 새로 만든다.**
문턱을 내리는 것도 **시작 전에** 정한다 — 시작한 뒤에 내리면 이미 포기한 분은 그 변경을 못 본다.

## 14. 사람이 정해야 남은 것

- [ ] **선물이 무엇인지 · 받는 곳과 시간 · 문의처** — 주보 광고를 넘기기 전에. 「상」이라는 말은 쓰지 않는다
- [ ] **공지가 언제 나가는지** — 기준선(§9)은 그 **전에** 떠야 한다
- [ ] 신청 때 **전화번호를 받을까**(`needs.phone`) — 받으면 `privacy/` 와 앱 안 화면 두 곳을 함께 고쳐야 하고,
      `event_signups` 에는 배부 뒤 번호를 비우는 장치가 없다(필사와 다르다). **안 받기를 권한다**
- [ ] 시작일을 옮기면 **`event_stamp_2026.sql` 과 `FEAT_SINCE.stamp` 두 자리를 함께** (7일 단위로만)

## 15. 왜 이 구조인가 (고른 것과 안 고른 것)

**A안(고름) — 기존 이벤트 플랫폼에 「자격」한 겹.** 새 표 0개. 규칙은 `needs.eligibility`,
진행률은 조회할 때마다 즉석 계산. 6주치 `daily_activity` 는 참여자 160명 × 42일이라 충분히 작다.

**B안 — 진행 스냅샷 표 + cron.** 조회는 빨라지지만 `daily_activity` 가 이미 매일
`v2_activity_drift()` 로 대조받는 것과 **같은 종류의 빚을 하나 더** 진다. 200명 규모에 과하다.

**C안 — 옛 퀴즈형(`event_entries`)을 고쳐 쓰기.** 회차를 `app_config('event')` 한 행에 담아
**다음 회차를 열면 지난 회차가 덮여 사라진다.** 2026-09-10 에 이벤트 플랫폼을 만든 이유가 그것이다.
