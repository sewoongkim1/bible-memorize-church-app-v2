# 사역신청 기획안 (2026-09-06)

> 상태: **초안 · 담당자 검토 전.** 근거 자료 — 「2026 사역신청서」·「2026년도 교회부서 조직」(사진 4장, 2026-09-06 제공).

해마다 종이로 걷던 「2026 사역신청서」를 로그인 앱 위에 얹어, 신청부터 임명 확정까지
한 화면에서 잇는 방안.

## 01. 배경

고척교회는 매년 성도에게 종이 「사역신청서」를 나눠 주고 걷는 방식으로 2026년도
사역(부서·팀) 참여를 받고 있다. 신청서에는 이름·교구-목장·직분·전화번호를 손으로
적고, 위원회 → 부서 → 팀(부) 3단계로 나뉜 약 **130여 개 사역팀** 중 최대 3개를
우선순위와 함께 표시한다.

이 방식의 어려움은 세 가지다.

- **집계가 사람 손을 거친다.** 수백 장의 종이를 부서별로 분류하고 엑셀로 옮기는
  작업이 매년 반복된다.
- **구조가 복잡한데 안내는 종이 한 장뿐이다.** 위원회 안에 부서, 부서 안에 팀, 팀
  안에 다시 「2부/3부/오후」 같은 선택지가 있어(찬양부·전도부 등) 어르신이 혼자
  정확히 표기하기 어렵다.
- **임명직과 신청 대상이 한 표에 섞여 있다.** 회계·팀장·리더 등은 신청이 아니라
  지명이라 신청서 뒷면에 별도 표로만 안내되는데, 눈에 잘 안 띈다.

이 앱은 이미 **교구-목장-이름** 식별자로 로그인하고 있고, 필사 노트 신청 같은
「신청 → 관리자 처리 → Web Push 안내」 흐름을 운영 중이다. 같은 뼈대 위에
사역신청을 얹으면 종이 없이도 같은 일을 할 수 있다.

## 02. 목표

1. **성도**가 앱에서 부서 구조를 눈으로 보고, 최대 3개 사역을 우선순위와 함께
   신청·수정·취소한다.
2. **담당자**가 부서·팀별 신청 현황을 화면에서 바로 보고, 겸직 여부를 참고해
   임명 상태(확정/보류/미채택)를 표시한다.
3. 확정되면 **이미 있는 Web Push 경로**로 신청자에게 한 번 알린다 — 지금처럼
   "게시판에서 직접 확인"에만 기대지 않는다.
4. 사역 구조·신청 기간은 **해마다 갱신**되므로, 코드를 고치지 않고 데이터만
   바꿔 다음 해에도 재사용한다.

## 03. 기존 자산 재사용

이 기능은 새로 짓는 것보다 **필사 노트 신청**의 뼈대를 그대로 옮기는 쪽에 가깝다.
신청 한 건 = 한 행, 상태가 단계별로 바뀌고, 상태가 바뀌면 Web Push가 한 번 나가는
모양이 똑같다.

| 필사 노트 신청 | 사역 신청(제안) | 재사용되는 것 |
|---|---|---|
| `pilsaApply` / `pilsaMine` / `pilsaCancel` | `ministryApply` / `ministryMine` / `ministryCancel` | 신청·내역조회·취소 3종 액션 패턴 |
| `pilsaList` / `pilsaSetStatus` | `ministryList` / `ministrySetStatus` | 관리자 목록·상태 변경, 확정 시 Push 1회 |
| 신청완료 → 준비중 → 준비완료 → 배부완료 | 신청완료 → 검토중 → 임명확정 / 미채택 | 단계형 상태값 + 관리자 전용 전환 |
| `identity_key`(교구·목장·이름)로 본인 확인 | 동일 | 로그인 정보 재사용 — 이름·연락처 재입력 불필요 |
| `pilsa_orders` 테이블, 최근 1건만 노출 | `ministry_orders` 테이블, 연도별 1건 | 테이블 설계·"한 건이 한 행" 원칙 |

⚠️ **재사용의 의미** — 이름·교구·목장·전화번호는 로그인 시점에 이미 있다. 신청서
상단 4칸을 성도가 다시 손으로 적을 필요가 없다 — 종이보다 오탈자가 적게 시작한다.

## 04. 사역 임명 원칙과 시스템화

신청서 상단에 적힌 6가지 원칙 중, 시스템이 그대로 강제할 수 있는 것과 사람 확인이
남는 것을 나눠야 한다.

| 원칙 | 내용 | 시스템 반영 |
|---|---|---|
| 1 | 등록식 후 3개월 이상 성실히 출석한 성도만 신청 가능 | **수동 확인** — 앱에 등록일 데이터가 없다. 안내 문구만 노출, 최종 확인은 사람 |
| 2 | 1인 최대 3개, 자치회장도 계수에 포함 | **자동 검증** — 신청 화면에서 3개 초과 선택 자체를 막는다 |
| 3 | 부장·팀장·회계·찬양대지휘자·자치회장은 다른 부서 동일 사역 겸직 불가 | **부분 자동화** — 임명 데이터가 쌓인 다음 해부터 경고 표시 가능. 1차년도는 관리자 검수 |
| 4 | 교사·찬양대원 이중사역 불가(새하늘찬양대 예외) | **부분 자동화** — 같은 이유로 참고 경고 수준, 확정 판단은 관리자 |
| 5 | 신청 후 임명받아야 사역 가능, 확인은 게시판 | **자동 검증** — 상태값 자체가 "신청완료→임명확정"이라 이 원칙을 그대로 구현한다 |
| 6 | 사역 신청은 매년 다시 | **자동 검증** — `ministry_orders`에 연도 컬럼을 두어 해마다 새로 받는다 |

⚠️ **1차년도 현실적 목표** — 3·4번 같은 겸직 규칙은 **사람 사이의 관계**(누가 어느
부서 팀장인지)를 시스템이 처음부터 알지 못하므로 완전 자동 검증은 무리다. 첫 해는
**3개 제한과 상태 흐름만 강제**하고, 겸직·자격 확인은 지금처럼 담당자가 눈으로 본다
— 종이보다 느려지지만 않으면 된다.

## 05. 사역 구조 데이터 — 두 원본의 불일치

받은 자료는 서로 다른 두 문서다. **①「2026년도 교회부서 조직」**은 부서마다
담당자 이름이 적힌 인사표이고, **②「2026 사역신청서」**는 성도가 표시하는 빈
신청 양식이다. 앱에 넣을 마스터 데이터는 성도가 실제로 고르는 **②**를 기준으로
삼아야 하는데, 두 문서를 맞대 보면 팀 이름이 정확히 일치하지 않는 자리가 여럿 있다.

| 부서 | ① 조직표(인사표) 기준 | ② 신청서(양식) 기준 |
|---|---|---|
| 찬양부 | 찬양대운영·찬양팀운영·오케스트라·주나힘찬양 등 *포함* | 위 4개는 *빠지고*, 대신 **비파와수금·베데스다**가 새로 등장 |
| 목양부 / L-12 | 운영·목양지원·**목양관리·서기·회계** | 운영·목양지원·**정착관리·소그룹 리더교육** |
| 예배부 | 회계(최현희) 한 줄이 별도로 존재 | 회계 항목 없음 — 성찬예식만 임명직 표에 별도 표기 |

⚠️⚠️ **전제조건** — 이 불일치는 개발로 풀 수 없다. 실제로 어느 이름이 맞는지는
신앙운동팀·해당 부서가 정해야 한다. **부록 표는 ② 신청서 기준으로 재구성**했고,
개발 착수 전 이 표 한 장을 담당자가 최종 확정해 주는 것이 1단계다.

### 3단계 구조와 하위 선택지

사역 구조는 대부분 *위원회 → 부서 → 팀* 2~3단계지만, 두 가지 예외가 있다.

- **어와나(교육위원회 · 사랑부 하위)** — 퍼글 / 커비 / 스팍스·티엔티 / 트랙·저니
  중 하나를 더 골라야 하는 4단계 구조.
- **주일찬양·수요찬양·행복전도대** — 팀은 하나인데 "2부/3부/오후", "오전/오후",
  "금/토" 중 **봉사 시간대를 하나 골라** 신청서에 표시하는 방식(라디오 선택).

데이터 모델에는 이 두 성격 — *깊이가 다른 트리*와 *같은 팀 안의 단일 선택 옵션* —
을 모두 표현할 수 있는 필드가 필요하다(부록 뒤 데이터 모델 참고).

## 06. 성도 화면 흐름

1. **안내** — 사역임명원칙 6조 + 유의사항을 한 화면에 먼저 보여준다(종이
   신청서의 첫 박스 그대로).
2. **내 정보 확인** — 이름·교구·목장·전화번호가 로그인 정보로 미리 채워져
   나온다 — 손으로 다시 적지 않는다.
3. **부서 고르기** — 위원회 단위 아코디언(기존 「가정 축복 기도문」 주제
   아코디언과 같은 방식)으로 펼쳐 팀을 고른다. 어와나·주일찬양처럼 하위
   선택이 있는 팀은 고르는 즉시 그 자리에서 시간대를 추가로 묻는다.
4. **최대 3개, 우선순위** — 3개를 넘겨 고르면 화면이 막는다. 고른 순서를
   1·2·3 우선순위로 보여주고 순서를 바꿀 수 있게 한다.
5. **제출 · 확인** — 제출 즉시 "신청완료" 상태로 저장. 마이페이지에서 언제든
   내역을 보고, 마감 전까지 고쳐 다시 낼 수 있다.
6. **임명 결과 알림** — 담당자가 임명확정으로 바꾸는 순간 Web Push 1회 —
   필사 신청 「준비완료」 알림과 같은 자리.

⚠️ **쓰기·채점을 넣지 않는다.** 가정 축복 기도문과 같은 이유다. 이건 「외우는
것」이 아니라 「신청하는 것」이라 진행률·점수 같은 장치를 넣지 않는다. 자판이
어려운 분도 목록에서 누르기만 하면 되므로 카드 모드 같은 별도 입력 방식도
필요 없다.

## 07. 관리자 화면 · 백엔드

제안 Edge Function 액션:

| 액션 | 주체 | 역할 |
|---|---|---|
| `ministryCatalog` | 공통 | 연도별 부서·팀 트리 + 임명직 여부 + 하위 선택 옵션 반환 |
| `ministryApply` | 성도 | 최대 3개 사역 + 우선순위 저장(마감 전 재신청 시 갱신) |
| `ministryMine` | 성도 | 내 신청 내역 조회 |
| `ministryCancel` | 성도 | 마감 전 신청 취소 |
| `ministryList` | 관리자 | 부서·상태별 신청자 목록, 우선순위 표시 |
| `ministrySetStatus` | 관리자 | 임명확정/보류/미채택 전환 — 확정 시 Web Push 1회 |

제안 테이블:

| 테이블 | 주요 컬럼 |
|---|---|
| `ministry_catalog` | `year, committee, dept, team, option_group, option_label, is_appointed, sort_order` |
| `ministry_orders` | `identity_key, name, gu, mokjang, phone, year, choices(jsonb: 팀id+우선순위+선택옵션 최대 3개), status, note, created_at, decided_at` |

관리자 화면은 새 페이지를 만들기보다 **`admin-stats.html`에 탭 하나**로 붙인다 —
성경암송 통계·필사 신청과 같은 자리에서 한 비번(`ADMIN_SECRET`)으로 이어 보게 한다.

## 08. 실행 로드맵

1. **데이터 확정** — 05장의 불일치를 담당자가 정리해 「팀명 최종본」 엑셀
   한 장으로 확정한다. 개발은 이 표가 나온 뒤 시작한다.
2. **백엔드** — `ministry_catalog`·`ministry_orders` 테이블과 6개 액션을
   개발 DB에 먼저 만들고 확인한다.
3. **성도 화면** — 안내 → 부서선택(아코디언) → 3개 우선순위 → 제출,
   마이페이지 내역 화면.
4. **관리자 화면** — `admin-stats.html`에 신청 현황·상태 변경 탭 추가.
5. **오픈** — 신청 기간에만 첫 화면에 노출(필사 신청처럼 상시가 아니라
   기간 한정이면 배너 자동 숨김 로직 포함), 종료 후 임명 처리·알림.

## 09. 확인이 필요한 사항

- **기간** — 신청 시작일·마감일이 언제인가. 상시 신청인지, 특정 2주 같은
  기간 한정인지에 따라 첫 화면 노출 방식이 달라진다.
- **데이터 정합성** — 05장의 조직표·신청서 불일치를 최종 확정할 담당자는
  누구이며, 언제까지 가능한가.
- **겸직 검증 범위** — 3·4번 원칙(겸직 제한)을 1차년도에 참고 경고로만 둘지,
  아니면 기존 임명 명단(교회부서 조직표)을 미리 데이터로 넣어 신청 단계에서
  부터 걸러줄지.
- **결과 통보** — 임명 확정을 앱 Push로 개별 통보할지, 지금처럼 "홈페이지
  게시판에서 확인"만 유지할지 — 둘 다 하는 것도 가능하다.
- **우선순위 입력** — 1·2·3 순서를 성도가 직접 정하게 할지(드래그 등),
  아니면 고른 순서를 그대로 우선순위로 볼지.

신청이 아니라 지명이라 이 앱의 신청 목록에는 넣지 않고, 참고용으로만 함께 적었다.
